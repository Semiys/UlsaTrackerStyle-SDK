# Авторизация, изоляция клиентов и мониторинг

Дата обсуждения: 31 октября 2026 года. Проверенный код: сервер 0.9.0.
Статус на 01.11.2026: жизненный цикл аккаунта и роли остаются планом. Аудит изоляции и отдельный мониторинг реализованы в 0.10.0; [результаты](SECURITY_AUDIT_2026-11-01.md), [запуск](MONITORING.md).

## Назначение хранилищ

Продуктовые события SDK принимает сервер API, проверяет пакет и ключ приложения и записывает события в ClickHouse. Прямое подключение телефона или браузерной SDK к ClickHouse не предусматривается. Аккаунты, проекты, приложения, хеши ключей и сессии сейчас находятся в отдельной SQLite-базе кабинета.

В локальной версии 0.10.0 Prometheus подключён для эксплуатационных метрик: доступность API, длительность запросов, ошибки, ресурсы контейнеров, скорость приёма событий и состояние очереди после её появления. Он не заменяет журнал событий ClickHouse. Не использовать идентификаторы отдельных событий, пользователей и сессий как метки Prometheus с неограниченным числом значений.

Источники: [назначение Prometheus](https://prometheus.io/docs/introduction/overview/), [правила меток](https://prometheus.io/docs/practices/naming/).

## Существующие границы доступа

1. Сервер проверяет сессию пользователя и принадлежность запрошенного приложения владельцу. Чужой идентификатор в URL не является разрешением.
2. В Grafana создаются отдельные организация, пользователь Viewer и источник ClickHouse для каждого владельца аккаунта. Приложения одного владельца доступны ему; отдельной модели сотрудников и проектных ролей пока нет.
3. Шлюз подставляет собственную Grafana-идентичность владельца. Переданные извне Basic Authorization и выбранный клиентом чужой orgId не используются как полномочия. Включённое демо отдельно разрешает публичную организацию 1.
4. Для владельца создаётся отдельный пользователь ClickHouse с SELECT на таблицу событий и политикой строк по разрешённым идентификаторам его приложений. Одного WHERE в SQL панели для безопасности было бы недостаточно.
5. ClickHouse и внутренний сервис Grafana не публикуются напрямую на хост. Открытый порт 3000 текущего приложения — шлюз Node.js, а не прямой административный порт Grafana.

Текущая изоляция логическая: база app и таблица events общие для клиентов. Это не отдельный физический ClickHouse для каждого пользователя. Оператор инфраструктуры обладает привилегированным доступом; его полномочия должны быть отделены от клиентского кабинета.

Роль Viewer не ограничивает пользователя только SQL-запросами показанных панелей. Поэтому ограниченный пользователь и политика строк на стороне БД являются существенной частью защиты. См. [документацию Grafana](https://grafana.com/docs/grafana/latest/setup-grafana/configure-security/).

## Что нужно до публичного размещения

- Отдельная конфигурация сервера с HTTPS, соответствующим PUBLIC_URL и Secure-cookie. Локальный HTTP остаётся только для разработки.
- Отключение публичного деморежима и отдельное рассмотрение анонимного доступа Grafana. При отключении анонимного доступа обновить проверку здоровья, которая сейчас опирается на локальный демостенд.
- Замена демонстрационных паролей ClickHouse и Grafana; безопасная передача и ротация секретов вне репозитория. Одно изменение переменной окружения не считать гарантией смены пароля в уже созданном томе.
- Минимальные права для записи событий и отдельные полномочия для создания пользователей/политик и миграций. Сейчас приложение использует привилегии для подготовки изоляции Grafana.
- Подтверждённые сетевые границы: наружу публикуется вход сервиса, внутренние административные интерфейсы и БД закрыты.
- Перед выпуском проверять применимость обновлений Grafana, ClickHouse, Node.js и плагинов к используемым версиям; обновления проверять в отдельном окружении.

## Полный жизненный цикл аккаунта

Уже есть регистрация и вход, scrypt с отдельной солью, серверные сессии с хешами токенов, CSRF-защита, ограничения попыток, выход и отзыв ключей. Срок сессии сейчас фиксированный — семь дней. Настройки Secure зависят от HTTPS в PUBLIC_URL.

Далее спроектировать и реализовать:

1. Подтверждение почты и защиту повторных отправок. Для неподтверждённых аккаунтов определить доступные действия.
2. Восстановление доступа одноразовым ограниченным по времени токеном; смену пароля и почты с повторной проверкой личности; безопасные ответы, не раскрывающие наличие аккаунта.
3. Список активных сессий, отзыв выбранной сессии и выход со всех устройств. Определить абсолютный срок и тайм-аут бездействия, обновление токенов и поведение при восстановлении аккаунта.
4. MFA для владельца и административных действий; одноразовые коды восстановления и понятный сценарий потери второго фактора.
5. Отдельное членство и роли в проекте. Предложение: владелец управляет проектом и доступами; администратор — приложениями и ключами; аналитик — отчётами и разрешённой выгрузкой; наблюдатель — просмотром. Точный набор разрешений согласуется до реализации. Просмотр графиков не должен автоматически давать управление ключами или выгрузку всех сырых данных.
6. Журнал входов и значимых изменений доступа, без паролей и полных токенов. Определить срок хранения и доступ к журналу.
7. Общие лимиты и хранилище состояния для нескольких экземпляров API. Текущие ограничения попыток находятся в памяти процесса, а SQLite кабинета — локальный файл; это отдельно учитывать при переходе к кластеру и нескольким датацентрам.
8. Повторная оценка параметров хеширования паролей и ограничений ресурсов; защита от массового перебора и регистрации без постоянных блокировок, позволяющих постороннему заблокировать жертву.

Практическая основа: [OWASP Authentication](https://cheatsheetseries.owasp.org/cheatsheets/Authentication_Cheat_Sheet.html), [Session Management](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html), [Forgot Password](https://cheatsheetseries.owasp.org/cheatsheets/Forgot_Password_Cheat_Sheet.html).

## Приёмочные сценарии следующего этапа

- Без сессии недоступны приватные проекты, панели, исходные события, CSV и ключи.
- Чужие appId, projectId, dashboard UID, orgId и datasource UID не открывают чужие данные.
- Изменённый или лишённый фильтра SQL в Grafana не выводит события постороннего владельца; отдельно проверяются недоступные таблицы, системные источники и внешние функции.
- Viewer не может писать в БД, создавать источники данных и выдавать права; проверка выполняется через API, а не только отсутствие кнопок.
- Смена ролей и отзыв членства обновляют доступ в кабинете, Grafana и ClickHouse; проверяются кэши, уже открытая вкладка и повтор старого запроса.
- Повторное использование и истечение токена восстановления отвергаются; смена пароля и выход со всех устройств отзывают предусмотренные политикой сессии.
- Подмена cookie, отсутствие CSRF, перебор паролей, перезапуск API и работа нескольких экземпляров проходят отдельные проверки.
- Для каждой проверки создаются независимые тестовые аккаунты и данные. Настройки и личная статистика существующих пользователей не изменяются.
