# Резервирование и восстановление

Инструмент 0.1.0, формат комплекта 1. Профиль: текущие шесть сервисов React/Express/ClickHouse/Grafana/Prometheus/Grafana оператора. Само приложение остаётся выпуском 0.11.2.

## Перед началом

Нужны Docker с Linux-контейнерами, Compose с поддержкой !override и Node.js 24 для служебного скрипта. Программы автоматически не устанавливаются. Если docker отсутствует в PATH, укажите полный путь в переменной DOCKER_BIN. Запускать команды нужно из репозитория с инструментом. У оператора должны быть права чтения конфигурации и секретов; исходные права скрипт не ослабляет. Родительские папки назначения нужно подготовить заранее, а сами snapshot/каталог восстановления должны быть новыми.

Первый вариант выполняет холодное резервирование: все исходные контейнеры должны быть заранее остановлены. Скрипт не останавливает и не перезапускает исходный сервис сам. Для остановки используйте ту же комбинацию Compose-файлов, с которой запущена система, и достаточный таймаут завершения. SDK может сохранять события в ограниченную очередь до возвращения сервиса.

Комплект содержит приватные данные и секреты. Храните его вне Git и публичных папок, на диске с ограниченным доступом. SHA-256 проверяет целостность, но не заменяет шифрование и не подтверждает доверие к чужому комплекту. Восстанавливать следует собственные проверенные копии. Наличие копии на том же ноутбуке не защищает от потери ноутбука или дата-центра: отдельное защищённое хранение вне исходного хоста остаётся следующим шагом.

## Создать копию

Пример PowerShell (каталог snapshot должен быть новым):

```powershell
New-Item -ItemType Directory -Path "D:\Backups\UlsaTracker\2026-11-07" -Force | Out-Null
node scripts/recovery.mjs backup --project mispisit-sarantsev --output "D:\Backups\UlsaTracker\2026-11-07\snapshot"
```

На Linux/macOS используйте абсолютный путь, например /srv/backups/ulsa/2026-11-07/snapshot. Для простого локального эксперимента можно передать --without-images, но тогда на целевом Docker должны уже существовать точные образы из manifest.json. Для переноса на другой хост включённые образы нужны; по умолчанию они сохраняются.

Комплект включает:

- appdata: учётные записи, проекты, приложения, хеши ключей и серверный секрет;
- dbdata: данные и схема ClickHouse;
- product_grafana_13: организации, источники данных и панели владельцев;
- prometheusdata: сохранённая служебная история;
- operatordata: состояние операторской Grafana;
- runtime-конфигурацию, локальные секреты и .env при его наличии;
- Docker-образы по фактическим image ID, включая вспомогательный Node;
- контрольные суммы архивов, конфигурации и образов, а также отпечатки деревьев файлов томов.

Read-only тома плагинов не копируются: они восстанавливаются из сохранённого образа приложения. Устаревшие неиспользуемые тома прежних версий не входят в комплект. Исходные тома монтируются помощником только для чтения. До и после копирования проверяется состояние контейнеров, а для каждого тома сравнивается отпечаток файлов до и после архивирования. Manifest появляется только после успешного завершения. Частичная папка без manifest.json не считается готовой копией.

Все фактические образы проверяются до большого копирования. Если контейнер ссылается на удалённый образ, нужно сначала восстановить этот образ или корректно пересоздать соответствующий сервис на его согласованной версии, а затем повторить резервирование.

## Восстановить отдельно

Пример PowerShell:

```powershell
New-Item -ItemType Directory -Path "D:\RestoreChecks" -Force | Out-Null
node scripts/recovery.mjs restore --input "D:\Backups\UlsaTracker\2026-11-07\snapshot" --project ulsa-recovery-proof --directory "D:\RestoreChecks\ulsa-2026-11-07" --port 18088
```

Требуются новое имя Docker-проекта и ещё не существующий рабочий каталог. Скрипт откажет, если целевой проект или его тома уже существуют, имя совпадает с исходным, контрольные суммы не сходятся или профиль не поддерживается. Старые тома он не очищает и не перезаписывает. При ошибке частично созданный тестовый стенд оставляется для диагностики; выбирать существующую папку для повторного запуска нельзя.

После проверки файлов загружаются недостающие сохранённые образы. Используются image ID, без неявного скачивания новой версии и без пересборки приложения. Перед извлечением проверяются имена архивных путей; после извлечения сравниваются содержимое, относительные ссылки, права и владельцы файлов тома. Затем копия запускается на своих сетях и новых томах.

Кабинет: http://127.0.0.1:18088. Prometheus: http://127.0.0.1:18089. Grafana оператора: http://127.0.0.1:18090. Все три порта привязаны к loopback; использовать нужно именно 127.0.0.1, чтобы cookie копии не смешивались с основным кабинетом на localhost. Должны быть свободны три последовательных порта. API и база отдельно не публикуются. Порт приложения внутри контейнера остаётся 8080.

Входите прежней учётной записью: её хеш пароля и ключи восстановлены из appdata. Не меняйте пароль и не отзывайте реальные ключи ради теста копии. Тестовые события, отправленные в восстановленный стенд, остаются в его базе и не дописываются в основной сервис.

## Проверка результата

1. Проверить состояние шести сервисов и версию /health.
2. Сверить данные проектов и приложений, а также счётчики/идентификаторы сохранённых событий.
3. Проверить вход и чтение своей статистики, отказ чужому владельцу.
4. Отправить синтетическое событие в копию с прежним ключом, повторить тот же пакет и подтвердить один учёт.
5. Проверить Grafana и CSV/JSON в выбранном периоде.
6. Зафиксировать длительность восстановления и фактическую точку копии. Сравнить с заранее выбранными целями RTO/RPO.

После проверки копию можно остановить с сохранением её данных:

```powershell
docker compose -p ulsa-recovery-proof -f "D:\RestoreChecks\ulsa-2026-11-07\docker-compose.yml" -f "D:\RestoreChecks\ulsa-2026-11-07\docker-compose.monitoring.yml" -f "D:\RestoreChecks\ulsa-2026-11-07\docker-compose.react.yml" -f "D:\RestoreChecks\ulsa-2026-11-07\recovery.override.yml" stop
```

[Первое фактическое восстановление и измерения](RECOVERY_QA_2026-11-07.md). Копия на том же Docker-хосте подтверждает процедуру, но не является испытанием потери физического сервера. ARM64, автоматическое расписание, шифрование, отдельное хранилище копий и восстановление на другом хосте проверяются отдельными этапами.
