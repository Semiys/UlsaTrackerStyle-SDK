# Стиль документации UlsaTrackerStyle SDK

Принято 15.10.2026. Ориентир — понятная навигация и подача документации Android Developers по Kotlin и Jetpack Compose.

## Цель

Разработчик должен быстро найти способ подключения для своей платформы, отправить первое событие и проверить его появление в панели. Названия разделов описывают задачи: «Подключить SDK», «Отправить событие», «Проверить доставку».

Документация пишется на русском; имена API и идентификаторы сохраняются как в исходниках. Стиль применяется к новым страницам; существующие руководства переводятся на него постепенно. Требования к оформлению учебных отчётов сохраняются отдельно.

## Структура

| Раздел | Содержание |
|---|---|
| Обзор | Для чего нужна SDK, что собирает, поддерживаемые платформы и ограничения. |
| Быстрый старт | Требования → подключение → инициализация → первое событие → проверка в панели. |
| Руководства | Одна задача на страницу: экраны, клики, успешные действия, свойства, очередь, повторы, отключение сбора. |
| Справочник API | Сигнатуры, параметры, значения по умолчанию, результат, ошибки и ограничения. |
| Примеры | Небольшие законченные интеграции: обычный Android, Compose; остальные платформы — после реализации. |
| Решение проблем | Симптом → возможная причина → конкретные проверки → ожидаемый результат. |
| Версии и миграции | Изменения для разработчика, совместимость и действия при обновлении. |

Документы по разработке сервера, архитектуре и лабораторным доступны отдельными группами в оглавлении. В пути первого подключения не должно быть необходимости читать историю лабораторных или рабочие заметки.

## Страница руководства

Использовать одинаковый порядок:

1. **Задача.** Что получится после выполнения инструкции.
2. **Перед началом.** Поддерживаемая платформа, версия SDK, необходимые настройки; ссылка на предыдущий шаг.
3. **Шаги.** Короткие нумерованные действия с кодом рядом с объяснением.
4. **Проверка.** Какое событие или состояние должно появиться, где это увидеть и сколько ждать.
5. **Ограничения.** Только условия, влияющие на этот сценарий.
6. **Дальше.** Ссылки на связанные руководства и справочник.

Вверху длинной страницы — оглавление с якорями. Внизу — следующий логический шаг. Заголовки и ссылки должны объяснять назначение страницы без соседнего текста.

## Примеры кода

- Для Gradle всегда подписывать файл: `settings.gradle.kts`, корневой `build.gradle.kts` или файл модуля приложения. Для Android указывать класс и место вызова: например, `Application.onCreate()`.
- Основной синтаксис — Kotlin и Kotlin DSL. Примеры Java, Groovy и JavaScript добавляются только при наличии соответствующей поддержки.
- Приводить необходимые импорты и зависимости. Если показан фрагмент существующего класса, явно назвать этот контекст; не выдавать такой фрагмент за полный файл.
- Использовать текущие имена публичного API и проверенные версии. Не описывать планируемые методы как готовые.
- Использовать нейтральные пути и явные заменяемые значения: адрес сервера, ключ приёма, имя приложения. Подписывать, откуда взять каждое значение.
- Инструкции для конкретного ноутбука и его пути хранить в документах локальной разработки. Общие руководства должны подходить другому разработчику.
- Не помещать ключ чтения или пароль кабинета в клиентский код. Учебные публичные ключи явно обозначать как демонстрационные.
- Рядом с отправкой события объяснять результат: принятие команды SDK не равно подтверждению записи на сервер. Успешное действие фиксировать после выполнения операции приложения.
- Для Compose объяснять место вызова, чтобы событие открытия экрана не отправлялось при каждой рекомпозиции.
- Полные примеры поддерживать в сборке или проверять компиляцией при изменении публичного API. Непроверенный пример явно отмечать.

## Справочник

Публичные Kotlin-методы документировать через KDoc: назначение, параметры, результат, особенности вызова и ссылки на руководство. Генерация справочника с Dokka запланирована; пока актуальное поведение описано в `SDK_API.md`. Установка генератора и публикация сайта не являются частью принятия этих правил.

Источник правды о поведении — код и тесты конкретной версии. Справочник и руководства должны обновляться вместе с изменением API.

## Навигация сайта документации

При создании отдельного сайта документации использовать:

- слева дерево разделов с отмеченной текущей страницей;
- в центре текст и примеры;
- справа оглавление текущей страницы на широком экране;
- на телефоне — сворачиваемое меню и доступное оглавление;
- поиск, якоря, копирование кода, ссылки на связанные темы;
- видимую версию SDK и платформу; переключатели платформ — по мере появления настоящих руководств;
- светлую и тёмную темы с цветами «Дома Коллекционера», читаемые таблицы и блоки кода.

Это требования к будущему сайту, а не описание уже реализованного интерфейса. Пока точка входа — `docs/README.md` на GitHub. Приём навигации и структура берутся за ориентир; тексты и оформление создаются для нашего продукта.

## Проверка страницы перед публикацией

- С первого экрана понятно, для кого страница и какую задачу решает.
- По инструкции можно пройти без знания структуры репозитория автора.
- Понятно, какие значения нужно заменить и где их получить.
- Есть ожидаемый результат и способ его проверить.
- Ссылки ведут к существующим страницам; запланированные разделы отмечены.
- Ограничения Android/JVM, локального подключения и публикации в Maven отражены честно; iOS и JS не представлены как готовые SDK.
