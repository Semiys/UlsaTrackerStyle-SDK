# Совместимость резервирования с ЛР5 — 15.11.2026

Проверена ветка PR №7 после совмещения с main `54b9980` (принятый PR №8). Инструмент резервирования — 0.2.0; сервер — 0.12.0. Код сервера, frontend, SDK, конфигурация ЛР5 и её опубликованные образы 0.0.5 сохранены. Новых тегов Docker Hub этим изменением не публиковалось.

## Что совмещено

- Разрешены конфликты README, Compose, package.json и плана. Сохранены оба списка проверок: operations из ЛР5 и recovery из PR №7.
- Инструмент принимает два точных набора сервисов: lab5 и monitoring-react. Их данные и Compose-файлы различаются; профиль фиксируется в manifest.
- Старый manifest формата 1 без поля profile относится к monitoring-react. Неизвестный профиль и несовместимый набор сервисов отклоняются до создания копии.
- API и БД восстановленного стенда не получают отдельные опубликованные порты. Кабинет, Prometheus и, при наличии, Grafana оператора доступны через loopback на новых портах.

## Автоматические проверки

Полный `npm run test:release` выполнен внутри Docker на отдельной базе: **143/143**, ошибок, отмен и пропусков нет. Включены серверные и JavaScript SDK-проверки, кабинет, ключи, изоляция владельцев, CSV/JSON, frontend-шлюз, Grafana, Prometheus, ingestion_receipts и восемь проверок защиты восстановления.

Для полного прогона использовался мониторинговый профиль с отдельным Compose-именем, новыми томами и локальными портами. Образ checks собирался из текущих исходников (`monitoring-test`); frontend взят из опубликованного 0.0.5. Проверка Grafana использовала определение панели именно этого профиля.

В каждом источнике отдельно создан синтетический владелец, проект, Android-приложение и ключ. После восстановления вход выполнен прежними реквизитами, приложение найдено в прежнем проекте, а старый ключ использован для повтора и нового события. Счётчики events и ingestion_receipts сверены непосредственно в ClickHouse FINAL по идентификатору контрольного приложения. Запись в восстановленную копию не изменила отпечатки исходных томов.

Указанное время измеряет вызов restore до healthy при локальных образах. Создание копии, перенос между компьютерами и отдельная загрузка images.tar в него не входят; это не итоговый RTO для потери хоста. Проверка старого формата выполнена на контролируемом комплекте текущего QA-стенда, а не на архиве прежних пользовательских данных.

## Условия и границы

Хост: Windows, Docker Desktop с Linux-контейнерами, Intel/amd64. CLI восстановления выполнен Node.js 24.22.1, контейнер checks — Node.js 24.22.2. Новый source-профиль имеет публичные настройки локальной ЛР5; мониторинговый профиль сохраняет свои секреты в приватном комплекте.

Реальные пользовательские контейнеры, тома, аккаунты и мобильные исходники в этих испытаниях не изменялись. Использовались только отдельные QA-проекты. Тестовые комплекты с секретами и синтетическими ключами не включаются в Git.

Не повторялись нативный ARM-хост, другой компьютер, отказ диска/дата-центра, длительная нагрузка, Android APK и iOS. Полный browser/device-прогон интерфейса не проводился заново; в этом этапе проверены HTTP-сценарии, production-маршруты frontend и реальная работа сервисов. Защищённое внешнее хранение, расписание и обновления инфраструктуры остаются отдельными задачами.

Инструкция для самостоятельной проверки: [резервирование и восстановление](BACKUP_AND_RESTORE.md). Прежние испытания SDK и восстановления сохранены в отдельных протоколах от 07.11 и 09.11.
