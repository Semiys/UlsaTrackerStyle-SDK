## Что меняется относительно предварительного плана

Фактическая тема — «Интерфейс и внешний вид рабочей версии». Резервное копирование, Kubernetes и регистрация проектов не являются заданием этой работы. 23.10.2026 пользователь отдельно решил расширить выпуск: включить регистрацию, проекты, приложения, ключи и JavaScript SDK. Это осознанное превышение функциональных границ методички, а не её требование.

Для аналитических систем прямо предписана готовая Grafana или Metabase. Собственные графики прежней страницы нельзя выдавать за выполнение этого требования.

## Выбранные ранее три функции

1. Создать аналитическое событие через форму либо SDK и записать его в ClickHouse.
2. Просмотреть события и статистику.
3. Получить объяснение отказа на ошибочные данные без создания записи.

Владелец приложения/разработчик работает с аналитикой; мобильное приложение отправляет события через SDK. «Дом Коллекционера» — первый клиент. Мобильное приложение не является сдаваемым интерфейсом: преподаватель открывает браузер и не устанавливает APK.

## Предлагаемое решение

- Сохранить Node.js, Express, EJS, формат событий и ClickHouse из ЛР3.
- Оставить в app главную с навигацией, форму отправки и страницу отказа. Для оформления выбрать локально включённую библиотеку; палитру приложения сохранить в серверных страницах.
- Статистику показывать в Grafana: пользователь выбрал этот вариант 22.10.2026. Metabase рассмотрен как альтернатива. Grafana выбрана также с учётом будущего мониторинга инфраструктуры.
- Compose: app:8080, db во внутренней сети, dashboard:3000. Сохранить имя mispisit-sarantsev и том dbdata с прежним путём.
- Предварительно настроить источник db и один готовый экран с названием UlsaTrackerStyle SDK 0.0.4. При первом запуске не должно быть мастера настройки или запроса на вход проверяющего.
- Обеспечить переходы из приложения к панели и обратно, к форме и отказу. Созданное событие видно после обновления панели.
- Счётчики событий/сеансов, события по времени, экраны, кнопки и последние события построить по реальным данным ClickHouse с теми же правилами повторного учёта, что у API. Не подменять их тестовыми числами.
- Учебный открытый просмотр сохраняется. Дополнительно реализованы частные кабинеты с отдельными организациями Grafana и политиками строк ClickHouse.

## Технические проверки перед реализацией

1. Grafana требует установленного ClickHouse datasource plugin. Проверить совместимость фиксированных версий; последний plugin нельзя автоматически сочетать с версией Grafana из примера методички. Плагин и конфигурация должны быть подготовлены без ручных действий проверяющего.
2. Если выбран Metabase, проверить поддержку ClickHouse выбранным тегом, автоматизацию первого запуска и готового экрана, постоянное хранение его настроек и потребление ресурсов.
3. Не переносить пример PostgreSQL db:5432 буквально: наша БД — ClickHouse, HTTP 8123 / native 9000 внутри Docker-сети.
4. Запросы панели должны учитывать ReplacingMergeTree и проект, чтобы повторная доставка события не увеличивала статистику.
5. Перед созданием ветки проверить незакоммиченные документы предыдущих обсуждений; не потерять их и не смешать с непроверенной реализацией.
