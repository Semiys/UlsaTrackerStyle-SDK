# Prometheus и физический TECNO — 01.11.2026

Проверена цепочка: действие в настоящем Android-приложении, доставка его SDK по локальной сети, запись ClickHouse, счётчики Prometheus и график Grafana оператора. Код приложения и серверная логика в ходе этого прогона не менялись; устанавливать новый APK не потребовалось.

- TECNO POVA 5 / TECNO LH7n, Android 14; «Дом Коллекционера» debug 1.5, versionCode 8; Kotlin SDK 0.2.0.
- Установленный APK совпал по SHA-256 с обычной локальной debug-сборкой. Проверены включение SDK и действующий ключ Android-приложения без вывода ключа в журнал.
- Сервер 0.10.1, ClickHouse 26.8.34.13, Grafana 13.3.0, Prometheus 3.13.5 LTS.
- Телефон и ноутбук находятся в одном сегменте Wi-Fi; endpoint APK `http://192.168.0.90:8080`. Список `adb reverse` пуст, USB использовался для диагностического доступа и запуска теста. Передача событий не шла через USB reverse.
- Запущен существующий инструментальный тест `ProductAnalyticsUiTest#configuredSdkUsesWifiAndQueuesRealEvent`: **OK (1 test)**. Он проверяет доступность /health и нажимает настоящую кнопку с реальным ProductEventTracker/SDK в изолированном интерфейсе. Сохранение, редактирование и удаление предметов не выполняются.
- Это проверка доставки и технических метрик на одном устройстве. Массовая нагрузка, батарея телефона, интернет-доступ к серверу и сеть вуза этим прогоном не проверены. Остановки API/БД и тревоги ранее испытывались отдельно в изолированном стенде, не повторялись на пользовательских данных сейчас.

Перед проверкой в телефоне находилось **21 накопленное событие**. Сверка по eventId показала, что все 21 доставлены. Первый прогон также добавил три свежие записи: `screen_view/sdk_setup`, `screen_view/collection` и `button_click/sdk_setup` со свойством `button=sdk_device_check`.

После окончания инструментального теста в журнале оставались три записи, уже присутствовавшие в ClickHouse. При следующем обычном запуске SDK повторила их передачу: `duplicate` вырос до 3, но повторных строк в БД не появилось. Подтверждённая очередь очистилась. Это проверка повторной доставки, а не утверждение о точной причине задержки сохранения ACK в завершившемся тестовом процессе.

Два обычных запуска приложения при проверке и завершении добавили ещё по одному открытию коллекции. Итого **26 новых для БД событий = 21 из прежней очереди + 5 новых записей тестового сценария и запусков**. Общее число строк ClickHouse выросло с 512 до 538; Android-приложения — с 400 до 426. Значение `ulsa_ingest_events_total{result="accepted"}` в Prometheus совпало с разницей БД: **26**. Показатель повторов — **3**.

Всего сервер наблюдал **6 запросов POST /api/v1/events, все HTTP 200**; метрика acknowledged тоже равна 6. Счётчики dropped и rejected в журнале SDK до и после равны нулю. В течение 45 секунд без действий accepted, duplicate и число строк БД не менялись; очередь оставалась пустой.

Все три цели Prometheus (`ulsa-api`, `clickhouse`, `prometheus`) имеют up=1. В Grafana оператора видны приём новых событий и повторов отдельными рядами, а также метрики CPU/RSS/задержек. График доставки показывает **события в секунду**, рассчитанные rate(), а не накопительное количество 26/3. Prometheus не получает тексты коллекции или сами строки продуктовых событий.

## Как повторить

1. Запустить основной сервис и мониторинг по [MONITORING.md](MONITORING.md), открыть кабинет приложения и панель оператора.
2. Убедиться, что endpoint APK указывает на доступный адрес ноутбука, а ключ принадлежит нужному приложению. localhost телефона требует отдельной настройки USB reverse; текущий прогон использует LAN-адрес.
3. Сначала проверить и учесть накопленную очередь: её доставка может прибавить много событий без новых нажатий.
4. Снять исходные счётчики, выполнить небольшое известное действие, дождаться отправки SDK и следующего 15-секундного опроса Prometheus.
5. Сравнить новые eventId и строки ClickHouse с accepted; повторные подтверждения учитывать через duplicate. Не сравнивать абсолютный счётчик процесса API со всей историей приложения.
6. Оставить телефон без действий и проверить стабильность счётчиков. Не изменять личную коллекцию ради проверки мониторинга.
