# ЛР5 — наблюдение за приёмом события, 0.0.5

Приложение: **0.12.0**. Ветка `lab5` основана на актуальной `main` (`6a7367c`, продукт 0.11.2), а не на сохранённой ветке ЛР4. PR: https://github.com/Semiys/UlsaTrackerStyle-SDK/pull/8.

## Решение

Выбрано наблюдение за сохранением аналитического события — действием прежней формы и SDK API. Уведомление человеку о каждом событии не нужно массовому автоматическому потоку. Email, SMS, мессенджеры, push, Mailpit и worker в этом выпуске не реализованы.

На третьем курсе проектировался «Дом Коллекционера». Нынешняя система — отдельный сервис аналитики для разных приложений, поэтому наблюдается приём аналитической записи, а не создание предмета коллекции.

Новая таблица `ingestion_receipts` создаётся приложением при запуске через `CREATE TABLE IF NOT EXISTS`. Она содержит `project_id`, `event_id`, `event_name`, `observed_at`, `status`; `event_id` логически связывает её с существующей строкой `events`. Это не ограничение FOREIGN KEY: ClickHouse его здесь не обеспечивает. Статус `stored` означает, что исходная запись сохранена и след сформирован. Старые события без следа автоматически не дополняются выдуманной историей.

Две записи в ClickHouse не являются одной транзакцией. При ошибке записи следа клиент не получает ACK. Повтор с тем же UUID восстанавливает недостающий след, исключая уже записанный исходник. На логическом чтении `FINAL` нормальные повторы не увеличивают число следов. Это не глобальная транзакция и не обещание exactly-once во всех распределённых сбоях.

Удаление приложения очищает обе таблицы; незавершённая очистка может безопасно повторяться. Reader Grafana имеет SELECT и row policy для каждой таблицы, приватные владельцы остаются разделены. Публичный `/api/demo/state` жёстко ограничен демонстрационным проектом, query-параметр не позволяет выбрать чужой.

## Интерфейс и API

Все обычные пользовательские маршруты отдаёт production-сборка **React + TypeScript + Vite**: кабинет, инструкции, форма, статистика, отказ, демонстрация JS SDK и состояние. Сервер Vite для запуска не нужен. Express остаётся API и шлюзом Grafana; старые EJS-обработчики сохранены для совместимости, но основной frontend-порт не использует их как страницы.

`/system-state` показывает HTTP-приложение, доступность БД и последнюю подтверждённую запись. На свежем томе след пустой. После формы видны число, UUID, тип, время и результат. Автообновление — 5 с; ручная кнопка не создаёт повторных запросов во время загрузки. При отказе БД ответ 503 сохраняет признак доступности самого приложения, а экран не показывает устаревшее «Доступно». Проверка БД ограничена по времени; frontend также прерывает зависший запрос.

| Метод | Назначение |
|---|---|
| GET `/api/demo/form` | UUID, сессия, время и подписанная сервером форма |
| POST `/api/demo/events` | Валидация и сохранение; JSON не более 8 КиБ |
| GET `/api/demo/state` | Текущее состояние и последний реальный след |
| GET `/api/demo/recent` | Исходные события демонстрации для сверки |
| GET `/api/demo/refusal-example` | Реальный результат валидатора для пустого имени без записи |

Форма не передаёт браузеру сырой ключ приёма. Все demo API отключены при `DEMO_MODE=0`. Существующий контракт SDK `/api/v1/events` сохранён; клиентские SDK и мобильный код этим выпуском не менялись.

## Графики и метрики

В демонстрационной Grafana один новый операционный показатель: время последнего приёма из `ingestion_receipts`. Основные продуктовые графики сохранены. Приватные панели используют существующий шаблон, без второго набора операционных панелей. Исторический шаблон ЛР4 не изменён: новый dashboard подключён отдельным файлом `grafana/lab5-dashboard.json`.

Библиотека `@prometheus-io/client` закреплена в package-lock. Prometheus опрашивает внутренний `app:9100/metrics` каждые 5 с. Счётчик `ulsa_ingest_events_total{result="accepted"}` растёт после подтверждения новых событий; повтор относится к `duplicates`. Счётчики процесса сбрасываются при перезапуске, записи ClickHouse сохраняются. `up{job="ulsa-api"}` проверяет доступность сбора метрик, а не наличие продукта в БД.

В будущем нужны сбор логов Loki/OpenSearch, ошибки Sentry/GlitchTip, внешняя доступность Uptime Kuma и трассировка OpenTelemetry/Jaeger; в ЛР5 они не развёрнуты.

## Развёртывание и версии

Команды находятся в первом разделе «Запуск» [README](../README.md). Root Compose не содержит `build`: опубликованные API и frontend имеют тег `0.0.5` и две платформы. Порты — 8080, 3000, 9090; порт ClickHouse не опубликован. Имя `mispisit-sarantsev`, сервис `db`, том `dbdata` и DB-подключение сохранены. Дополнительно остаются `appdata` и `grafanadata`; добавлен `prometheusdata`.

Версии сохранённого стенда ЛР4: ClickHouse 26.8.26.12, Grafana 11.4.0; Prometheus закреплён на v3.13.5. Это воспроизводимый локальный показ, не заявление об актуальности всех инфраструктурных версий. Перед внешней эксплуатацией необходимы согласованное обновление и повторный аудит. Основной пользовательский стенд 8080 этим выпуском автоматически не обновлялся.

## Отличие от методички

По прямому решению автора завершён перенос всего интерфейса на React и добавлен отдельный `frontend`-контейнер. Это осознанное отступление от требований сохранить платформу и не добавлять новый frontend в ЛР5. Оно прямо отражено в отчёте; нельзя утверждать буквальное соблюдение этих двух ограничений. Основной результат наблюдения, старые функции, данные и способ запуска сохранены.

Методичка требует Intel; автор дополнительно выбрал ARM. Проверка ARM выполнена под эмуляцией на Intel, не на физическом ARM-компьютере. Объединение PR в main выполняется после просмотра. Ветка `lab5` должна остаться доступна.
