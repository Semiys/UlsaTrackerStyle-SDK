## Цель и границы первой версии

Собственная система продуктовой аналитики: мобильная библиотека → API приёма → хранение событий → веб-статистика. Первый клиент — «Дом Коллекционера» (DomCollection) на Android. Общий код SDK планируется на Kotlin/KMP; iOS и отдельная JavaScript библиотека добавляются после работающего мобильного сценария.

Первая проверяемая цепочка: нажать кнопку в мобильном приложении → получить событие на сервере → сохранить его в DuckDB → увидеть увеличение счётчика. Тема не ограничивается коллекционерами: сервер и SDK должны принимать события разных приложений, каждое в своём проекте.

## Независимость от магазина и назначение SDK

Пользователь хочет применять SDK при публикации приложения в разных магазинах, включая AppGallery и RuStore. Приём обычных продуктовых событий планируется через собственный HTTPS API, без обязательной зависимости от служб конкретного магазина, рекламных идентификаторов и платёжных SDK. Доступность сервера и совместимость клиента всё равно требуют проверки в целевых сетях и на устройствах.

Готовый MyTracker уже поддерживает приложения разных магазинов: это указано в [документации добавления приложения](https://docs.tracker.my.com/ru/environment/application/about). Поэтому обоснование разработки — собственная инженерная система, управление контрактом событий, доставкой, данными, отчётами и масштабированием. Нельзя утверждать в отчёте, что своя SDK необходима потому, что MyTracker работает только в RuStore.

SDK — подключаемая библиотека, а не отдельное приложение. KMP означает Kotlin Multiplatform: общий Kotlin-код событий и доставки с платформенными частями. Первая библиотека подключается к Android; iOS проверяется позже на подходящем окружении. SDK не требует, чтобы каждое приложение, в которое её встраивают, было написано на KMP: для обычного Android приложения предусмотрим понятный интерфейс Kotlin/Java. Node.js/Express принимает запросы, DuckDB хранит события, код браузера рисует графики из серверной статистики.

## События и подключение SDK

Начальные события: `screen_view`, `button_click`, `action_success`. Примеры постоянных имён: `collection`, `add_model`, `model_saved`. Успех сохранения фиксируется после успешной операции; нажатие и успех — разные события.

Реализованный контракт: `schemaVersion` на уровне пакета; события содержат `eventId`, `sessionId`, `occurredAt`, `name`, `screen`, `platform`, `appVersion` и ограниченные `properties`. `projectId` определяется по ключу, серверное время поступления хранится отдельно. Точные правила — `EVENT_CONTRACT.md`.

SDK не отправляет запрос на каждое касание отдельно: помещает событие в ограниченную очередь и отправляет пакет в фоне. Размер пакета, время отправки, предел очереди, срок хранения и политика удаления при переполнении будут явными настройками. При ошибке сети или 429 выполняется ограниченный повтор с паузой; устойчивый `eventId` сохраняется между повторами. Ошибка аналитики не должна мешать приложению сохранять модели или переключать экраны.

Автоматическую регистрацию всех касаний, содержимого полей, фотографий, коллекций и экранных снимков не планируем. Разработчик явно отмечает полезные действия. Скролл, если понадобится, записывается как достижение порога/раздела с ограничением частоты, а не каждое изменение координат.

Ключ приёма, встроенный в клиент, нельзя считать скрытым паролем администратора. Управление проектами и просмотр аналитики требуют отдельных прав. Перед публичным размещением нужны ограничение размера/частоты запросов, изоляция проектов, срок хранения событий и понятный способ отключить сбор в клиенте.

## Переход от одного контейнера к нескольким

Первый вариант с БД:

```text
Android/KMP SDK → [API + DuckDB + запросы статистики + веб-страницы]
                  один контейнер, один процесс-владелец БД
```

Планируемое разделение:

```text
SDK → балансировщик → приёмники API → долговечная очередь
                                           ↓
                                  запись и запросы DuckDB
                                           ↑
                                  API статистики / веб
```

Процесс хранения один владеет каждой базой DuckDB; запросы и запись проходят через него. Копии приёмника API не монтируют файл БД для записи. Контейнер хранения читает очередь пакетами, подтверждает обработку после записи и повторно распознаёт уже принятые события по идентификаторам. HTTP-ответ о приёме должен иметь явный смысл: в монолите — подтверждённая запись; после разделения — подтверждённое помещение в долговечную очередь, а не обещание немедленного появления в графике.

Официальная документация [DuckDB](https://duckdb.org/docs/current/connect/concurrency) описывает чтение/запись одного процесса в обычном встроенном режиме. Поэтому увеличение числа контейнеров API не означает увеличение числа независимых писателей одного файла. Новые серверные режимы DuckDB/DuckLake требуют отдельного выбора и проверки; в начальную архитектуру они не заложены.

Очередь сглаживает всплески и сохраняет принятые события, но не увеличивает бесконечно скорость БД. Если запись постоянно медленнее поступления, растёт задержка. После измерений рассматриваем разделение хранилищ по проектам, архивирование в Parquet, предварительные агрегаты и пределы хранения. Для проекта, превышающего возможности одного владельца, отдельно проектируем распределение данных; замена DuckDB другой БД не выполняется незаметно.

## Что означает «3 миллиона пользователей»

Число установок, активных пользователей за сутки и пользователей одновременно — разные величины. Само число установок не задаёт нагрузку.

Иллюстрация, не доказанная производительность системы: 3 000 000 активных пользователей в сутки × 20 событий = 60 000 000 событий/сутки, примерно 694 события/с в среднем. Если каждый запрос содержит ровно 10 событий, средняя нагрузка — около 69 запросов/с. Таймеры отправки неполных пакетов, повторы и всплески увеличивают число запросов.

Для сценария проверки можно отдельно рассчитать десятикратный пик: около 6 944 событий/с. При среднем размере события 500 байт это около 30 ГБ исходных данных в сутки без учёта HTTP, индексов, сжатия и резервных копий. Все числа основаны на выбранных допущениях и должны заменяться реальными измерениями.

Измеряем: события/с, запросы/с и размер пакета; p95/p99 ответа; CPU и память; задержку появления в графике; длину/возраст очереди; потерянные, отклонённые и повторно учтённые события; объём БД и время восстановления. Отдельные проверки — сеть без связи, повтор одного пакета, перезапуск API/писателя, изоляция двух проектов и влияние SDK на слабый Android-телефон.

Обещание поддержки 3 млн пользователей пока не делается. Учебная задача — показать расчёт, работающие механизмы масштабирования, измеренные пределы и дальнейший путь.

## Заморозка предыдущего сервиса

`D:\Projects\collector-transfer-service` оставлен отдельным проектом. Его исходники и готовые исправления сохраняются; развитие импорта, CAPTCHA и AI-конвертации прекращено по решению пользователя. Ключи и пользовательские файлы прежнего сервиса в этот проект не переносятся.

Пользователь установил Docker Desktop на ноутбук после освобождения/выделения места, чтобы ускорить свою работу. Локальные проверки завершены; второй ПК остаётся дополнительным окружением. Агент программы не устанавливал. Исходные методички не редактируются; коммиты и пуш выполняет пользователь.

Характеристики ноутбука: i5-13500H, около 16 ГБ ОЗУ. После увеличения раздела C:, перед первой сборкой было свободно около 73,3 ГБ на C: и 43,8 ГБ на D:. Данные Docker оставлены на C: по последнему решению пользователя. Предлагаемый лимит WSL — 4 ГБ памяти и 4 логических процессора — не применён. Это стартовое предложение для небольшого сервиса, не гарантия предельной нагрузки или отсутствия троттлинга. ARM-эмуляция может замедлять сборки. Фактическое место и нагрев зависят от образов, кэша и запущенных задач.
