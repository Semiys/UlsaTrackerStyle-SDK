# Результаты прототипа DuckDB / Quack

Дата: 13.10.2026. Версия эксперимента: 0.1.0. Платформа запуска: Linux AMD64 в Docker Desktop / WSL 2 на Windows.

## Проверенная конфигурация

- Node.js 24.21.0, существующий `@duckdb/node-api` 1.5.6-r.1 и существующий `AnalyticsStore`.
- Официальный образ `duckdb/duckdb:1.5.6`, индекс `sha256:6f42e04517e2445b525d105dcfd12ef774c30d29f7e124c72daaf655fcffc0bb`.
- В публичном индексе есть `linux/amd64` и `linux/arm64`. Выполнение этого эксперимента на ARM не проверено.
- Сервисы `app` и `db`, отдельная сеть Compose, именованный том `dbdata` только у `db`. Клиент работает в памяти, файл базы ему не смонтирован.
- Три независимые проверки использовали проекты `mispisit-sarantsev-quack-probe`, `mispisit-sarantsev-quack-clean` и `mispisit-sarantsev-quack-final`.

## Что прошло

| Проверка | Результат |
|---|---|
| Загрузка Quack в официальном фиксированном образе | Успешно |
| Подключение Node.js к пустой базе по сети | Успешно |
| Автоматическое создание существующей схемы через серверный запрос | Успешно |
| Запись события и выдача ACK существующим AnalyticsStore | Успешно |
| Пять параллельных повторов одного события | Одна запись, все повторы распознаны |
| Тот же eventId с другим содержимым | Конфликт отклонён |
| Откат транзакции в присоединённой серверной сессии | Событие осталось |
| Статистика, последние события и свойства со знаком апострофа | Успешно |
| Подключение с неверным токеном | Отклонено |
| Физическая сохранность после down и up без -v | Прямой quack_query прочитал одну сохранённую запись |

## Что не прошло

1. Прямой `INSERT ... ON CONFLICT` в присоединённый каталог возвращает `Not implemented Error: GetStorageInfo not implemented yet`. Поэтому эксперимент временно направляет фиксированные SQL-запросы через официальный вызов `remote.query()`.
2. После удаления и пересоздания контейнера базы `ATTACH` к уже заполненной схеме возвращает `Binder Error: Catalog "remote" does not exist!`. Повторено на двух независимых томах, включая новый том, на котором все DDL выполнялись только серверными запросами. Замена клиентского имени каталога на `analytics` также не помогла.
3. Прямой `quack_query()` позволяет прочитать сохранённую запись без ATTACH. Однако отдельные вызовы BEGIN, INSERT и ROLLBACK в этом режиме не сохраняют общую транзакцию: ROLLBACK возвращает `cannot rollback - no transaction is active`. Так нельзя без изменения семантики подменить соединение существующего AnalyticsStore.

Исходная причина ошибки присоединения в реализации Quack не установлена. Проверки подтверждают сохранность файла и воспроизводимую ошибку клиента; они не доказывают повреждение базы.

## Вывод

Сеть, запись и сохранность DuckDB подтверждены. Проверка повторного подключения существующей логики после пересоздания контейнера не пройдена. Поэтому Quack 1.5.6 в проверенной конфигурации пока не принят как основное хранилище ЛР3. Нельзя считать готовой всю лабораторную или выпускать на основании этого эксперимента итоговый образ 0.0.3.

После последней проверки сервер переведён на ClickHouse отдельным блоком — [LAB3.md](../../docs/LAB3.md). SDK и опубликованные теги 0.0.1 и 0.0.2 не изменены. Контейнеры эксперимента остановлены; три тестовых тома сохранены для диагностики. Изменения находятся в ветке `lab3`, без коммита и публикации.

## Дальнейший выбор

- Продолжить проверку DuckDB после исправления Quack или на другой официально поддерживаемой конфигурации.
- Выбрать серверную СУБД для ЛР3. ClickHouse прямо разрешён методичкой для аналитики событий; перенос потребует отдельного проектирования повторов и конфликтов, а не только переписывания SQL. PostgreSQL — вариант для сохранения текущей транзакционной семантики на первом этапе.

В последней проверке `mispisit-sarantsev-quack-final` запись снова прошла, а после down/up присоединение каталога повторно завершилось той же ошибкой. Похожая проблема описана в открытом [issue Quack #247](https://github.com/duckdb/duckdb-quack/issues/247); общая первопричина независимо не установлена.
